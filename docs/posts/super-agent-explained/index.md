> 一个人同时能跟进 3 到 5 个活跃会话。这个数字不是模型的上限，是人的上限。

先把名字说清楚，因为绝大多数讨论都在这上面跑偏。

**「Super」在这里指的是「上层」，对应 Sub-agent 里的「Sub」。** 不是"超级"，也不是"更强的 Agent"。它是叠在原有 Agent 之上的一层协调机制，统一管理和分配任务——这是 DeepSeek 产品部崔添翼（该文审稿人之一）在知乎上给出的解释。

名字定下来，整套设计的意图就清楚了：它不试图让单个 Agent 更聪明，它要解决的是**你手上同时开着五个窗口，来回搬运上下文**这件事。

2026 年 10 月 31 日，DeepSeek Harness 团队发布《Super-agent 设计探索：迈向更自主的 Agent 系统》，同天在 GitHub 开源原型 `deepseek-ai/dsh-superagent-prototype`（MIT）。原文开头就声明：这是架构思路探讨，**不是对现有产品功能的介绍**。结语也强调，原型"只是一种为了验证技术路线而提供的原型，并非 DeepSeek 的正式产品"。

## 一、瓶颈不在模型，在人的注意力

单任务 Agent 已经证明能干活。问题出在多任务：你要推进三件事，就得开三个会话，每个会话的上下文互不可见，你得自己记住"A 会话里定过方案 A、B 会话里改成了 B"。

原文的观察是，一个人通常只能同时跟进 **3 到 5 个**活跃 Session。

这句话把上限拆成了两半：**单任务的上限取决于模型能力，多任务的上限取决于人的注意力。**

在这个框架下，"再训一个更强的模型"解决不了多任务问题。你要的是一套能替人管会话的调度结构。原文给这类形态下的定义是：**打破 Agent 与单次手动会话的绑定，使它成为能跨会话保持上下文、同时推进多项复杂任务且互不干扰的连续实体。**

## 二、四个特征

这四个特征是验收标准，不是宣传语：

| 特征 | 原文含义 | 缺了会怎样 |
| --- | --- | --- |
| 连续 | 在 IM、GitHub 评论等熟悉界面交互，感觉**始终只存在一个 Agent**，不必想"Session X 里有没有 Y 信息" | 用户自己拼上下文，方案从 A 改成 B 时 Agent 不知道 |
| 高效 | 响应快，能并行且高质量完成多个复杂任务，上一条没跑完就能接第二条 | 长任务阻塞新消息，或新消息打断长任务 |
| 主动 | 持续观察环境事件并主动推进，**不需要介入时保持安静** | 用户得轮询状态 |
| 持久 | 始终在线、接入真实工作环境、**长期运行中异常自动恢复** | 关机即停，重启丢掉续点 |

**单个 ReAct Loop 支撑不了这四条。** 一个循环是串行的：它无法同时满足"连续"（要稳定的全局视角）和"高效"（要多个互不干扰的执行单元）。这一条矛盾直接推出了下面的双层结构。

## 三、五个模块

原文的对应关系是：双层架构兼顾连续与并发，事件驱动实现主动，面向人的交互同时做到连续与高效，计算/状态/环境分离加 Watchdog 实现持久在线与自愈。

| 模块 | 解决什么 | 一句话 |
| --- | --- | --- |
| 双层架构 | 连续 vs 并发的权衡 | Router 管全局，Worker 管执行 |
| 事件驱动 | 主动性从哪来 | 输入从"人打的字"换成"环境事件" |
| 面向人的交互 | 一个任务跨渠道续着做 | 异步启动 + 分渠道说话，IM 单次不超过 100 词 |
| 计算、状态、环境分离 | 跨设备持久在线 | 云端算、数据库存状态、端侧只留轻量 daemon |
| Watchdog | 异常自愈 | 独立控制回路，看的是"有没有进展、有没有跑偏" |

## 四、双层：Router 不干活，Worker 不吭声

这是整套设计里最反直觉的一处。

**Router 层不执行具体任务，甚至可以不配备 Bash 工具。**

它的定位是常驻的全局路由层，承接所有入口的人类交互，充当全局的**序点、协调点和记忆**。原文的判断是，Router 的活常常没想象中复杂，**用较轻量的模型就能兼顾速度与效果**。

这里有一组我原来没写、但很关键的实测，说明单个常驻 Router 会话为什么没成为瓶颈。测试条件：Router 调真实模型、Worker 用 Mock 模型，Trigger 到达速率从每分钟约 1 条逐步提到约 40 条。

| 指标 | 1 条/分钟 | 40 条/分钟 |
| --- | --- | --- |
| 平均 batch 大小 | 1.0 | 2.8 |
| 单次请求耗时 | 2.5 秒 | 3.9 秒 |
| **单个决定分摊的推理时间** | 6.4 秒 | **1.6 秒** |

事件越密，排队越多，合并成一次调用后在 Prefill 阶段并行算，**每个决定分摊的时间反而下降了 75%**。这就是"积压越多越划算"的出处，也是原文敢说"当前团队规模下不必过早水平切分"的依据。

**Worker 层反过来：上下文隔离、挂满执行工具、通常配最强的模型、不直接跟人说话。**

Worker 的推理和工具调用不输出到外部渠道，只向 Router 汇报状态，由 Router 统一回人。多个 Worker 在同一个 PR 上撞车时，它们订阅同一个 Thread，收到相同的事件通知，自己发现冲突；少数跨任务协调由 Router 中转。Worker 内部还可以再建 Subagent、或本身就是一个 Agent Team，对上层透明。

一句话总结本质：**它不是"分工"，是把连续性和吞吐量拆到两层，各自只优化自己那一半。**

## 五、主动从哪来：Trigger 加两道筛网

真实群聊是"高噪音、低触发率"。每条都让模型读一遍，延迟和成本都撑不住。原文借了操作系统里的 Fast Path / Slow Path：

| 层 | 形态 | 职责 |
| --- | --- | --- |
| 程序层（快路径） | 确定性代码 | 按来源、群组范围、用户/机器人白名单做准入。每个来源可配成"仅响应明确请求""作为候选""直接忽略" |
| 语义层（慢路径） | LLM 判断 | 剩下的候选事件交给模型，按**提示词里写的策略**判断该不该动 |

程序层先滤掉大部分，语义层用自然语言写规则——**改策略改一句提示词就行**，不用发版。这是整套设计里最实用的地方。

过滤完还有一层路由优化。同一个 PR、同一个 IM 话题、同一封邮件串下的连续事件构成一个 **Thread**：

- **已订阅（快路径）**：后续事件由程序直通给已订阅的 Worker，不再经 Router 转发
- **未订阅（慢路径）**：Router 仍观测所有事件以掌握全局，但只用它判断和分派新事件
- **多对多**：一个 Worker 可订阅多个 Thread，一个 Thread 也可被多个 Worker 订阅

这条"直通"值多少钱，原文给了对照实验——把直通去掉，任务完成时间基本不变，但：

- Router 需要做的决定 **增加约 30%**
- 总读缓存 token 从 **2323 万增加到 3177 万，涨幅约 37%**

**省下来的不是时间，是钱和 Router 的注意力。** 这也解释了为什么它和"主 Agent 转发一切"是两种东西。

上下文的管理方式照着缓存做，原文有句话我认为是整节的核心：**"浪费上下文窗口，就是浪费模型的智能。"**

三步走：从最少信息开始，只给 ID 加摘要；再按局部性逐步 Inline，比如正文前 50 字、IM 消息的前后相邻消息和它回复的那条；超出预算就 Spill，只留引用。配合 Trigger、Thread、Worker 的唯一 ID 构成引用图，支持多跳召回——这就是链式召回。

再往前一步是投机执行，原则是**"结果有价值就交付，没有价值就丢弃"**。

## 六、面向人的交互：100 词的规定

这一节我原来漏了，但它对做产品的人最有用。

经典 ReAct Loop 里，模型发起一次同步的 `run()` 工具调用后，循环就阻塞了。原文的改法是换成异步的 `start()` 和 `stop()`：模型调用 `start()` 后立即收到"已启动（Started）"的返回，可以继续接新消息。

这个异步机制**已经在 DeepSeek Harness 里实现，但没有默认开启**。

然后是按信道分工：

| 信道 | 定位 | 规则 |
| --- | --- | --- |
| IM（即时通讯） | 低打扰的轻量沟通 | **单次回复不超过 100 词** |
| GitHub、邮件、文档 | 结构化、高信息密度的异步交付 | 完整记录留在任务里 |

那个 100 词的硬性规定值得单独拎出来。它不是文案建议，是**把"注意力成本"变成了可执行的约束**——超过 100 词，说明你在群里汇报过程，而不是给结论。

## 七、分离与看门狗：24 小时在线怎么成立

**计算与状态分离**：推进 Agent Loop 的计算放进云端无状态的弹性容器，Session 这类持久化状态存入数据库。云端机器重启，记录还在。

**计算与执行环境分离**：这条路对比了两种常见做法——云端沙箱重建环境成本很高，让用户整体迁往云端又太重。它的方案是**让重状态的执行环境留在原地，只在端侧部署一个不保存会话状态的轻量 daemon**。原文明确这是 BYOM（Bring Your Own Machine）。

顺带说一句，这跟 Anthropic 的"脑手分离"（Decoupling the brain from the hands）思路一致，但场景不同：那篇讲的是托管服务、客户 VPC 内的资源；这篇面对的是**用户日常使用、可能间歇在线的个人电脑**。同一个原则，两种落点。

**Watchdog** 是一个独立于主系统的控制回路。原文点出一个容易被忽略的事实：**许多异常并非进程崩溃，而是模型在执行中陷入无效循环或偏离目标。** 所以它的做法是起一个独立的 Watchdog Session，用定时消息驱动它，判断各个 Worker 有没有实质进展、方向有没有偏离，维护者还能用自然语言问它故障原因，让它在线修正主系统行为。

普通的进程存活监控在这里没用——灶台的灯亮着，不代表厨师没在放第三遍盐。

## 八、它和"主 Agent + 子 Agent"不是一回事

这是最容易混的地方，也是原文专门反驳的一点。

Anthropic 早前有篇《Building Agents》，核心观点是搞一堆子 Agent 不如单个 Agent 效率高。两个说法看起来矛盾。原文的回应是：**它们解决的不是同一层的耦合。**

| 维度 | Agent Team（主 Agent + 子 Agent） | Super-agent（Router + Worker） |
| --- | --- | --- |
| 主节点职责 | 理解任务细节、拆子任务、高频协调 | 只听需求、记背景、决定推给谁 |
| 主节点推理负担 | 重 | 轻，可用小模型 |
| 子单元之间 | 步骤强耦合，需频繁同步 | 上下文隔离、彼此独立 |
| 解决粒度 | 一个复杂任务内部怎么拆 | 多个任务之间怎么排队 |
| 冲突处理 | 主 Agent 协调 | 订阅同一 Thread，各自发现 |

我的读法：**两者不矛盾，是不同粒度上的两个答案。** 一个复杂任务拆解时，Team Lead 必须理解细节，Router 那种"不管细节"的策略会失效；十个互不相干的任务排队时，让主 Agent 深入每个细节是纯浪费。原文自己也承认这个边界——Worker 内部可以再起 Subagent 或 Team。

所以判断标准不是"哪个更先进"，是**你手上的问题是单任务太复杂，还是多任务太拥挤**。

## 九、最强的能力是"闭嘴"

原型 README 里有一句话，我认为是这套设计的价值观：**尽可能少占用人的注意力，尽可能多地提供价值。**

它把每条消息、每个通知、每个问题、每个设置项都算作注意力成本。规定也很具体：Agent 工作时保持安静，只在三种情况下开口——结果可用、需要人做决定、任务无法完成。

对比很扎心。同样是群里有人报 Bug 没人 @：

- 普通 Agent：先回"收到，我正在分析"，十分钟后发一段过程，半小时后说没复现。它很忙，你被折腾半天。
- Super-agent：后台复现、定位、试修。没复现出来或修复复杂，**全程不说话**；确认问题且方案简单，直接提 PR 交人验收。

**"闭嘴"不是能力不够，是产品能力。** 判断"该不该打扰人"比判断"能不能做"更难。

边界是写死的：只在被请求时、或书面规则明确允许时行动。没有人直接要求的任务，团队得预先写下规则。这一点在真实产品里也一样——下面会看到。

## 十、那组数字，和它的前提

原文第 7 节的消融实验，条件必须说清楚，否则数字会被误读：

- 同时注入群聊和 GitHub CI 两条事件流，单次约 **300 条消息**，其中约 **20 条**是真实工作请求
- 编码工作用纯耗时工具替代——**测的是调度与协作，不是单任务执行质量**
- 消息间隔与工作时长按 **1/4** 缩放，模型调用延迟保持真实
- 每种方案重复 **5 次**

| 配置 | p50 | p95 |
| --- | --- | --- |
| Super-agent | **12.4 分钟** | **15.7 分钟** |
| 单 Session + Subagent（中性提示） | 20.4 分钟 | 29.5 分钟 |
| 单 Session + Subagent（优先委派） | 13.8 分钟 | 29.0 分钟 |

中间那行的细节最值钱：**中性提示词下，5 次实验里模型一次都没调用 Subagent**，所有活全挤在主会话，被新消息反复打断。换成"优先委派"的提示词后，5 次里有 4 次成功委派，剩下那 1 次模型自己判断"这活小"就自己干了，造出了 29.0 分钟的 p95 长尾。

这组数字证明的是**调度结构有效**，不是模型更强。而且 p95 的差距（15.7 对 29.5）比 p50 更能说明问题——难受的从来不是平均值，是那几次全堵在一起的时候。

作者自己标注了：合成负载、简化环境、每配置只跑 5 次，**只能当初步参考**。这句话要跟着数字一起引用，否则就是耍流氓。

## 十一、产品端已经走到哪一步

概念讲完，得看有没有人真做出来。这儿有一份实测可以参考：十字路口团队用 **LobeHub**（前身是 LobeChat，2026 年初更名转向多 Agent 协作）搭了个"AI 选题编辑部"，三位成员：

- **主编**：跑在云端，只接需求、拆任务、分派、汇报，自己不做具体工作
- **调研员**：跑在云端，负责联网检索、核实一手来源
- **素材管理员**：跑在本机的 Claude Code，整理本地文件夹里的截图

形态上和 Router/Worker 很像，几个细节值得记：

**人只面对一个入口。** 主编全程只在线程里发了 3 条消息：已派出的任务、进度和待决定的问题、最终结论。频道没被刷屏，完整报告留在任务详情里。

**关键词唤醒，但先问人。** 主编配了"选题""能写吗""值得写"三个关键词，没人 @ 也会被唤醒。但它创建完任务后先问了一句"现在两个都开始吗？"——因为执行会消耗积分。**主动不等于擅自花钱**，这个分寸比"能不能主动"更难拿。

**追问回到原任务。** 用户在主线程里追问，主编没新建任务，而是把追问写成一条"追加需求"评论附在原任务下，状态从已完成改回进行中。这就是"Thread 订阅"在产品层的样子。

**关掉电脑照常工作。** 云端 Agent 在线，需要动本地文件时通过"执行设备"调本机，文件不上传。

**返工留在任务里。** 那份对照表做了三轮：第二轮验收 4 项挂了 1 项（只交了对照表，没和原报告合并），主编写返工说明，第三轮 4 项全过。全程人没介入。

也有限制，而且说得很实在：Slack 上三个 Agent 虽然能互相 @，**任务衔接仍然需要主编完成**；GitHub 集成还是 Alpha 阶段；LobeHub 创始人自己提了个想了三个月的问题——Agent 在团队里干活，**调用成本谁承担、用谁的资源、产出归谁**，尤其在创建者和任务发起者不是同一个人的时候。

最后一句提醒很重要，也是我引用这份实测的原因：**LobeHub 和 DSH 是各自独立的探索，只能说是"产品形态相近"，不能说"技术架构相同"。** 写这个概念的时候特别容易滑向后者。

## 十二、代价，和真正的天花板

原文没藏成本：

**token 明显更多。** 多会话本身增加消耗，Router 批处理、投机执行、后台提前干活都在烧钱。原话就是拿更多 token 换人的时间与注意力。

**Router 是单点。** 单个常驻会话够用，是因为团队规模小。规模上去只能分片，而一分片就丢连续性。

**长程记忆是主要瓶颈。** 原文说的是：运行周期拉长到跨月甚至更长，长程记忆便成为制约可扩展性的主要瓶颈。

然后是原来被我漏掉、但可能是最重要的一节——**安全与隐私**。原文的表述很硬：

> 如果没有办法很好地解决安全与隐私问题，那么 Super-agent 只有在一个很小且可信的范围才能工作。

两条具体风险：

1. **云端 Agent Loop 一旦遭遇服务端入侵或提示词注入而被攻破，它连接的全部端侧设备都面临被控制的风险。** 这不是"某个任务出错"，是把你在每台机器上的权限一次性交出去。
2. **只要端侧环境里的凭据能进入模型上下文，正常执行过程中也存在凭据泄露风险。** 所以需要设计一种机制，让 Agent 在**完全不接触凭据本身**的前提下使用凭据。

这条约束比"模型够不够聪明"重要得多。它决定了 Super-agent 的可用边界：**它是一个权限系统，然后才是一个 Agent。**

原型本身也别当产品用。README 写得很清楚：研究原型、面向单个 GitHub 仓库、可选接飞书、文中部分设计尚未实现、异步任务机制实现了但没默认开启。

## 十三、什么时候不该上

看信号，不看热度：

| 该上 | 别上 |
| --- | --- |
| 多个 issue / 团队话题同时要跟进 | 一次性的单点任务 |
| 长任务经常被新消息打断 | 任务之间没有共享环境 |
| 用户在花时间轮询 Agent 状态 | 没人愿意先把授权规则写清楚 |
| 任务需要不同目录、不同身份隔离 | 你只需要一个更长的提示词 |
| 想要主动发现，但不接受无限制自主 | 你无法承担多出来的 token 和权限风险 |

如果这些压力都不存在，一个边界清晰的 Personal Agent 更简单、也更好维护。**Super-agent 的复杂度是靠持续的事件流入、并行执行和可恢复状态挣回来的**，没有这三样，它只是更贵的聊天框。

---

原文结语有句话，我觉得比"AGI"这类词实在得多：

> 我们并没有提出全新的理论，而是将计算机系统中经典的工程思想应用到了 Agent 系统的构建中。

Fast/Slow Path 来自操作系统，存算分离来自分布式系统，投机执行来自 CPU，控制回路来自控制论。这套设计的价值不在发明，在**认出了这些老问题在新场景里的同一个形状**。

而它真正提出的问题也不是"Agent 能有多自主"，是**产品该不该把 Session 暴露给用户**。原文的答案是"让用户手动管理 Session，很大程度上是从底层 LLM API 延续下来的设计惯性"——会话是系统的实现细节，用户要管的是任务。

这句话对做工具的人比做模型的人更有用。你现在手里那套交互，是照着任务的形状设计的，还是照着 API 的形状设计的？
