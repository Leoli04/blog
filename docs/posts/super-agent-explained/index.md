> 一个人同时能跟进 3 到 5 个活跃会话。这个数字不是模型的上限，是人的上限。

2026 年 10 月 31 日，DeepSeek Harness 团队发了一篇设计长文《Super-agent 设计探索：迈向更自主的 Agent 系统》，同天在 GitHub 开源了原型 `deepseek-ai/dsh-superagent-prototype`（MIT，README 明确写着是研究原型、不是官方产品、代码为对外发布做过适配、与内部版本不一致）。

这篇文章提出的是**架构问题**，不是产品功能。理解它的关键，是先接受一个前提：现在主流 Agent 以「一次会话」为基本单位，会话之间互不相通。

## 一、瓶颈不在模型，在人的注意力

单任务 Agent 已经证明能干活。问题出在多任务：你要推进三件事，就得开三个会话，每个会话的上下文互不可见，你得自己记住"A 会话里定过方案 A、B 会话里改成了 B"。

据 DSH 团队的观察，一个人通常只能同时跟进 **3 到 5 个**活跃会话。

这句话把上限拆成了两半：**单任务的上限取决于模型能力，多任务的上限取决于人的注意力。**

在这个框架下，"再训一个更强的模型"解决不了多任务问题。你需要的是一套能替人管会话的调度结构。这就是 Super-agent 的出发点——不是让 Agent 更聪明，是让它同时管住更多事，且不找你汇报。

## 二、四个特征

原文给的四个特征，构成一组验收标准：

| 特征 | 含义 | 缺了会怎样 |
| --- | --- | --- |
| 连续 Continuous | 在 IM、GitHub 评论这些原有工作界面里交互，感觉始终只有一个 Agent | 用户得自己拼上下文，方案从 A 改成 B 时 Agent 不知道 |
| 高效 Productive | 一条指令没跑完就能接第二条，多任务并行且质量不掉 | 长任务阻塞新消息，或新消息打断长任务 |
| 主动 Proactive | 不等指令，监听环境事件自己推进，该沉默时沉默 | 用户得轮询状态，把 Agent 当需要喂饭的工具 |
| 持久 Persistent | 始终在线，接真实工作环境，异常后自动恢复 | 本地设备一关机就全停，重启丢掉续点 |

**单个 ReAct Loop 支撑不了这四条。** 因为一个循环是串行的：它无法同时做到"连续"（要一个稳定的全局视角）和"高效"（要多个互不干扰的执行单元）。这一条矛盾直接推出了下面的双层结构。

## 三、五个模块

| 模块 | 解决什么 | 一句话 |
| --- | --- | --- |
| 双层架构 | 连续 vs 并发的权衡 | Router 管全局，Worker 管执行 |
| 事件驱动 | 主动性从哪来 | 输入从"人打的字"换成"环境事件" |
| 全双工多渠道交互 | 一个任务跨渠道续着做 | 任务在后台跑，你在任意渠道追加/叫停 |
| 计算、状态、环境分离 | 跨设备持久在线 | 大脑、任务记录、代码文件分三处放 |
| Watchdog | 异常自愈 | 不只看进程死没死，还看任务有没有进展、方向有没有跑偏 |

第三、四、五个模块容易被忽略，但它们才是"24 小时在线"能不能成立的前提。特别是分离那一条：**把 Agent 的大脑放在云端、任务记录单独持久化、代码和文件留在原来的机器上。** 云端机器重启，记录还在；要动你的电脑时再远程连过去。这解决的是"进程崩了上下文就没了"这个最土的问题。

## 四、双层：Router 不干活，Worker 不吭声

这是整套设计里最反直觉的一处。

**Router 层不执行具体任务，甚至可以不配 Bash 工具。**

它的定位是全局的定序点、协调点和记忆：接住所有入口的人类交互，汇总跨任务的信息与决策，决定每件事交给谁，但自己不动手。原文的判断是，Router 的活常常没想象中复杂，**用较轻量的模型就能兼顾速度与效果**。

这里有个工程细节值得单独拎出来：单个常驻 Router 会话为什么没成为吞吐瓶颈？因为上一轮推理期间到达的事件会积压，在下一轮一次性注入，天然形成批处理。Router 每步是"长输入、短输出"，合并后的多条 Trigger 在 Prefill 阶段并行算，**单次请求耗时的增长远慢于批次大小的增长**。在一定范围内，积压越多，每个决定分摊的推理时间越低。上限是上下文长度，和模型一轮能准确处理多少条事件。

**Worker 层反过来：上下文隔离、挂满执行工具、通常配最强的模型、不直接跟人说话。**

Worker 的推理和工具调用不输出到外部渠道，只向 Router 汇报状态，由 Router 统一回人。这样既保住并发，又避免五个会话各说各话。多个 Worker 在同一个 PR 上撞车时，它们订阅同一个 Thread，会收到相同的事件通知，自己发现冲突；少数跨任务的协调由 Router 中转。

一句话总结这个结构的本质：**它不是"分工"，是把连续性和吞吐量拆到两层，各自只优化自己那一半。**

## 五、主动从哪来：Trigger 加两道筛网

主动性的代价是噪音。真实群聊是"高噪音、低触发率"——绝大多数消息跟 Agent 无关，每条都让大模型读一遍，延迟和成本都撑不住。

DSH 借了操作系统里的 Fast Path / Slow Path：

| 层 | 形态 | 职责 |
| --- | --- | --- |
| 程序层（快路径） | 确定性代码 | 按事件来源、群组范围、用户/机器人白名单做准入。每个来源可以配成"仅响应明确请求""作为候选""直接忽略" |
| 语义层（慢路径） | LLM 判断 | 剩下的候选事件才交给模型，按提示词里写的策略判断该不该动 |

程序层先滤掉大部分，语义层用自然语言写规则——**想改策略改一句提示词就行**，不用发版。这是这个设计最实用的地方。

过滤完还有一层路由优化：同一个 PR、同一个 IM 话题、同一封邮件串下的连续事件构成一个 **Thread**。Router 只为 Thread 的首个事件创建 Worker，之后该 Worker 直接订阅这个 Thread，**后续事件由程序直接投递，不再经过 Router**。只有没人订阅的事件才回到 Router 派发。

这是它和"主 Agent 转发一切"最本质的差别：主 Agent 是中心化的，每条消息都要过它；Super-agent 里 Router 只在冷启动和跨任务协调时出场。

上下文的管理方式也照着缓存做：Inline 把大概率要用的信息拉进窗口，Spill 把超预算的内容留在窗口外当引用，配合 Trigger、Thread、Worker 上的唯一 ID 做按需多跳召回。再往前一步是投机执行——根据环境信号在后台先做一部分，用户真提需求时直接交付。

## 六、它和"主 Agent + 子 Agent"不是一回事

这是最容易混的地方。看到 Router 分派 Worker，第一反应是"不就是主 Agent 带几个子 Agent"。

Anthropic 早前有篇《Building Agents》，核心观点是搞一堆子 Agent 不如单个 Agent 效率高。两个说法看起来矛盾。DSH 的回应是：**它们解决的不是同一层的耦合。**

| 维度 | Agent Team（主 Agent + 子 Agent） | Super-agent（Router + Worker） |
| --- | --- | --- |
| 主节点职责 | 理解任务细节、拆子任务、高频协调 | 只听需求、记背景、决定推给谁 |
| 主节点推理负担 | 重 | 轻，可用小模型 |
| 子单元之间 | 步骤强耦合，需要频繁同步 | 上下文隔离、彼此独立 |
| 解决粒度 | 一个复杂任务内部怎么拆 | 多个任务之间怎么排队 |
| 冲突处理 | 主 Agent 协调 | 订阅同一 Thread，各自发现 |

我的读法：**两者不矛盾，是不同粒度上的两个答案。** 一个复杂任务拆解时，Team Lead 必须理解细节，这时候 Router 那种"不管细节"的策略会失效；反过来说，十个互不相干的任务排队时，让主 Agent 深入每个细节是纯浪费。原文也承认这个边界——Worker 内部可以再创建 Subagent，甚至本身就是一个 Agent Team，对上层 Router 透明。

所以判断标准不是"哪个更先进"，是**你手上的问题是单任务太复杂，还是多任务太拥挤**。

## 七、最强的能力是"闭嘴"

原型 README 里有一句话，我认为是整篇设计的价值观：**尽可能少占用人的注意力，尽可能多地提供价值。**

它把每条消息、每个通知、每个问题、每个设置项都算作注意力成本。不能提供足够价值的，就该删掉。规定也很具体：Agent 工作时保持安静，只在三种情况下开口——结果可用、需要人做决定、任务无法完成。

对比很扎心。同样是群里有人报了个 Bug 没人 @：

- 普通 Agent：先回"收到，我正在分析"，十分钟后发一段过程，半小时后告诉你没复现。它很忙，你被折腾半天。
- Super-agent：后台复现、定位、试修。没复现出来或发现修复很复杂，**全程不说话**；确认问题且方案简单，直接提 PR 交人验收。

这个例子还展示了跨渠道的连续性：问题先在 IM 群里出现，后续有人在 GitHub 评论里要求换个修法，同一个 Worker 接着在 GitHub 上继续，不需要重新起会话。

**"闭嘴"不是能力不够，是产品能力。** 它要求系统能判断"这件事该不该打扰人"，这比判断"这件事能不能做"更难。

边界也是写死的：只在被请求时、或书面规则明确允许时行动。没有人直接要求的任务，团队得预先写下规则。Anthropic 的 Duet 是同款思路——能自己读信息、起草回复、准备工作，但发消息、付款、签文件、删除内容之前必须等人批准。

## 八、那组数字

原文第 7 节给了一个消融实验。条件要说清楚，否则数字会被误读：

- 同时注入群聊和 GitHub CI 两条事件流，单次约 **300 条消息**，其中约 **20 条**是真实工作请求
- 编码工作被替换成纯耗时工具，**测的是调度与协作，不是单任务执行质量**
- 消息间隔和工作时长按 **1/4** 缩放，模型调用延迟保持真实
- 每种配置重复 **5 次**

结果：

| 配置 | p50 | p95 |
| --- | --- | --- |
| Super-agent | 12.4 分钟 | 15.7 分钟 |
| 单会话 + Subagent 工具，中性提示词 | 20.4 分钟 | 29.5 分钟 |
| 单会话，delegate-first 提示词 | 13.8 分钟 | 29.0 分钟 |

中间那行有个细节：**中性提示词下，5 次实验里模型一次都没调用 Subagent**，所有活全挤在主会话，被新消息反复打断。换成 delegate-first 提示词后 5 次里有 4 次委派成功，剩下那一次模型自己判断"这活小"就自己干了，造出了 29.0 分钟的 p95 长尾。

这组数字证明的是**调度结构有效**，不是模型更强。而且 p95 的差距（15.7 对 29.5）比 p50（12.4 对 20.4）更能说明问题——真正难受的从来不是平均值，是那几次全部任务堵在一起的时候。

作者自己也标注了：负载是合成的、环境是简化的、每配置只跑 5 次，**只能当初步参考**。

## 九、代价，以及它什么时候不值得

原文没藏成本：

**token 明显更多。** 多会话设计本身就增加消耗；Router 批处理、投机执行、后台提前干活，都在烧钱。DSH 原话就是拿更多 token 换人的时间与注意力。

**Router 是单点。** 单个常驻会话够用，是因为目前团队规模小。规模上去只能分片，而一分片就丢连续性——原文直说"在全局记忆问题被解决之前，这一权衡始终存在"。

**全局记忆没解决。** 系统管的是任务状态，不是"这个团队过去半年积累了什么"。

**原型不是产品。** README 说得很清楚：研究原型、面向单个 GitHub 仓库、可选接飞书、文中部分设计尚未实现、异步任务机制虽然实现了但没有默认开启。

所以判断该不该上，看信号，不看热度：

| 该上 | 别上 |
| --- | --- |
| 多个 issue / 团队话题同时要跟进 | 一次性的单点任务 |
| 长任务经常被新消息打断 | 任务之间没有共享环境 |
| 用户在花时间轮询 Agent 状态 | 没人愿意先把授权规则写清楚 |
| 任务需要不同目录、不同身份隔离 | 你只需要一个更长的提示词 |
| 想要主动发现，但不接受无限制自主 | 你无法承担多出来的 token |

如果这些压力都不存在，一个边界清晰的 Personal Agent 更简单、更好维护。**Super-agent 的复杂度是靠持续的事件流入、并行执行和可恢复状态挣回来的**，没有这三样，它只是更贵的聊天框。

---

一个可以带走的判断：这套设计真正提出的问题不是"Agent 能有多自主"，而是**"产品该不该把 Session 暴露给用户"**。

DSH 的答案是不该——"让用户手动管理 Session，很大程度上是从底层 LLM API 延续下来的设计惯性"。会话是系统的实现细节，用户要管的是任务。

这句话对做工具的人比做模型的人更有用。你现在手里的那套交互，是照着任务的形状设计的，还是照着 API 的形状设计的？
